# 查房发布验收

单元测试通过不等于网站已经可用。每次调整采集、排队、缓存或自动刷新，都要同时检查下列三层，并保留同一部署版本的证据。线上观察未完成时，状态只能写“待验证”。

已完成的线上记录：[2026-10-14，70 分钟验收](./acceptance-results/2026-10-14.md)。

## 自动回归

`npm test` 包含完整功能测试；`npm run test:acceptance` 单独运行本次的查询生命周期用例。CI 自动执行离线回归，不在 CI 中访问真实官网或发送邮件。

- 三个日期页共用同一网络，等待首批结果的前五秒每秒刷新，首分钟其余时间每 2 秒刷新，之后每 10 秒刷新，连续十分钟不会被当作异常流量；补查有独立的单次和每日预算。
- 三个 90 站区间共享 260 个公开任务名额。部分入队、腾出名额、再次入队与公平调度都要走真实 SQLite，不只检查首批结果。
- 活跃查询每次刷新续期；离开查询页面五分钟后，尚未完成的普通任务释放名额。不能因新日期不断查询而给已离开的日期续期；已采集快照保留。
- 模拟 90 分钟，包含官网临时失败、后台定时采集、多个缓存周期，以及离开页面 25 分钟后重新查询。每个区间均需恢复完整新鲜结果。
- 缓存有效期边界前 1 毫秒仍有效，到边界立即过期。旧正数不能继续当作可订房源，失败、缺失与明确零值不能混淆。
- 页面缓存也要过期：网络中断时不能无限显示旧计数；收藏只记住驿站，换日期后没有当前新鲜观测时显示“房源待确认”，不能沿用收藏时的余房数。
- 持久采集锁保证多访客去重，等待中的 Cron 优先获得下一轮。最坏等待加采集仍少于每调用 50 条 SQL。
- 只扣实际尝试的官网请求；空批次与未使用的预留额度返还。剩余不足一整批的每日额度仍可使用，旧租约不能返还新租约的额度。
- 补查 API 固定最多 6 次官网请求、并发 6，不接受调用者指定站点、日期、URL 或扩大预算。隐藏页面、完整查询与不可信补查地址不会启动补查。
- 前台快速补查至多一分钟，按共享一秒启动间隔连续推进，完成或页面隐藏即停止。无到期任务时按真实的下一次重试时间等待，不额外错过退避结束时刻。
- 查询响应缓存只保存已完成的公开结果，最多一分钟且不能越过最早样本或目录的有效期；缓存命中仍执行限流，提醒和带凭据请求不进入缓存。
- 普通定时采集将取得锁和规划读取、最终写入分别合并为事务批次；没有活跃提醒且目录不需刷新时只需两次 D1 往返；过期所有者不能写入或释放新锁。
- Worker 和实际 `npm start` 的 HTTP 转换都要验证，避免内存 Request 测试漏掉真实 HTTP 的空请求体差异。
- 精简列表保留过滤、排序和计数；点击驿站后仍能加载原始官方详情链接。默认 API 保留完整字段兼容性。

模拟时钟用于验证状态和调度，不能代替官网网络耗时或云端 CPU 测量。

## 本机真实接口与页面

运行 `npm start`，实际请求 `/api/available`。待更新时调用响应中固定的 `meta.collection.advanceUrl`，以无请求体的 `POST /api/collection` 补查。然后检查页面自动出现新结果、详情能打开、官方链接有效，且没有浏览器错误。测试过程中关闭邮件发送。

## 固定版本线上持续验收

```bash
npm run acceptance:live -- \
  --url https://youth-inn-finder.imshunsukez.workers.dev/ \
  --minutes 70 --fast --tail --output .data/acceptance-<新的运行名称>
```

输出目录必须是新目录，避免混入旧证据。脚本只访问公开查房、日历、健康检查和有限补查，不创建提醒、不发送邮件、不读取用户令牌。测试会消耗现有免费查询与采集额度；不开启额外付费服务。

脚本从上海今天推导三个未来入住区间，可用 `--offset 15` 等参数更换一组尚无新鲜缓存的日期。使用当前个人上架房源目录作为分母，而不是假定目录永远恰好 90 个站点。所有成功响应必须具有相同的 `X-Deployment-Id`；中途更新网站就要重新验收。

| 阶段 | 实际行为 | 验证目标 |
| --- | --- | --- |
| 第 0–10 分钟 | 三个区间同时查询，使用与网页相同的有限快速补查；首分钟每 2 秒读进度，完成或超过窗口后每 10 秒读 | 公平调度、完整覆盖、正常流量限额 |
| 第 10–35 分钟 | 停止区间查询，仅每分钟看健康和日历 | 连续 25 分钟没有前台补查，Cron 仍更新数据，区间缓存自然过期 |
| 第 35–70 分钟 | 恢复三个区间查询 | 旧计数不冒充新鲜数据，恢复完整覆盖，并跨过下一个 20 分钟周期 |

以下是性能优化后 `--fast` 模式的验收阈值，须在测试前确定，不能为了让结果通过事后放宽。不带 `--fast` 时保留上一轮的兼容性阈值（首批45秒、查全10分钟、响应p95三秒），不能用它证明秒级查询。已有验收记录不改写。

| 指标 | 通过条件 |
| --- | --- |
| 首批有效采样 | 每个区间 5 秒内；明确零值也属于有效结果，不要求一定有可订房源 |
| 三个全市区间查全 | 每个区间 90 秒内，全部快照新鲜且计数已知；首次全市精确查询不等于1秒查全 |
| 自然过期 | 离开 25 分钟后的首次查询，新鲜数为 0，旧结果不作为当前余房展示 |
| 过期恢复 | 恢复查询后每个区间 90 秒内重新查全，后续缓存周期也能完成 |
| 查询响应 | 成功查询响应 p95 不超过 1 秒；官网采集耗时另计 |
| HTTP 可用率 | 全部探测至少 99%；正常三日期流量出现任何 429 都不通过 |
| 连续采样 | 每分钟心跳，连续缺口不得超过 2 分钟；机器休眠后只经过了 70 分钟不能算通过 |
| 数据正确性 | 覆盖分母守恒；返回的房源是已知正数且样本未超过 20 分钟；零与未知不能伪装成有房 |
| 后台运行 | 空闲阶段日历采样时间推进，新鲜覆盖不低于 85%；不出现采集任务整体失败 |
| 运行限制 | 至少 20 条同版本运行时观测；没有 CPU/内存超限导致的终止 |

`report.json` 分开报告 **functional** 和 **cpu**。功能 `PASS` 只证明这个观察窗口满足上述功能指标；CPU 出现超过免费 10ms 的成功调用时仍标记 `BUDGET_RISK`，不能宣称长期符合免费预算。实际超限终止则功能验收也失败。70 分钟通过不等于数天稳定性、任意并发量或官网永不故障。

原始采样只保存时间、部署 ID、覆盖数、耗时、稳定错误码与经过筛选的运行结果；不保留请求头、正文、完整 URL、邮箱、令牌或原始日志。汇总结果应记录到 PR 或验收结果文档，并注明起止时间、代码提交、部署版本与未通过的指标。

平台依据：[Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)、[版本元数据](https://developers.cloudflare.com/workers/runtime-apis/bindings/version-metadata/)。
