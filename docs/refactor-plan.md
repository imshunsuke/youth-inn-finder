## 1. 产品目标与已确认的决定

做一个公开的上海青年驿站找房网站，手机和电脑打开链接即可使用。界面采用米白、森林绿和精致住宿卡片；让用户先选入住时间，再筛选驿站，最后前往官网申请。

| 决定 | 用户已确认的内容 |
| --- | --- |
| 使用方式 | 公网网站，供多人使用 |
| 功能范围 | 日历、入住区间查询、区域/关键词筛选、距离排序、收藏、官方入口、后台监控和有房通知 |
| 账户 | 查房免登录；邮箱验证后建立提醒，通过邮件专属链接管理和取消，无注册/密码系统 |
| 通知渠道 | 邮件 |
| 官网读取边界 | 保留官方只读 POST 余房查询；不提交申请、不登录、不修改官网数据 |
| 资源与预算 | 暂无服务器、云账号和域名，尽量免费 |
| 协作方式 | 按计算机应届生水平解释影响和推荐理由；关键决定及时询问；减少手动点击，采用社区成熟方案 |
| 界面简洁度 | 尽可能简洁，不要面包屑文字；去掉装饰性英文小标题和重复说明，保留必要数据状态 |
| 欢迎区例外 | 用户提供截图并确认保留完整欢迎区：大标题、短文案、房屋插画和安心贴纸；其余部分继续简洁 |
| 首发容量 | 免费试用规模，最多 30 份占位提醒；查房用户不占提醒名额 |
| 区间提醒范围 | 单日可关注全市，连续入住邮件提醒必须指定驿站；普通连续入住查询仍保留 |

## 3. 页面与用户流程

### 找房

界面只保留主任务需要的标题、筛选和操作，不加面包屑或装饰性多层小标题。主要正文与按钮约 14px 起，手机上的核心信息不缩成难读小字；必要的未知/过期/失败状态用简短文字说明。

1. 首页直接展示上海日期下的未来 21 天概览，默认选择最早开放日期。
2. 入住日期必选，离店日期可选。区间查询使用官方连续入住余房接口；不能用每天数量的最小值推断同一房间可连续入住。
3. 常用筛选：行政区、关键词；高级项：个人/全部房源、只看上架、最低房数、数量/距离排序。
4. 驿站卡展示名称、地址、区域、当前查询的可用量、可选距离、收藏和官网详情入口。
5. 定位只在点击“按距离排序”后请求；显示直线距离，不能写成通勤距离或路程。
6. 完整站点日历按需展开，避免每张卡重复一大份日历。

### 邮件提醒

1. 用户按当前查询条件点击“有房提醒”。
2. 明确显示监控日期/区间、区域或站点、最低房数，填写邮箱。
3. 系统发送验证邮件。验证完成之前不启用监控、不发送有房通知。
4. 邮件专属链接可以查看、暂停、修改、取消自己的提醒；不用密码，不暴露其他人的记录。
5. 修改条件后建立新版本，取消旧条件尚未发送的通知；入住日期过期后自动结束提醒。
6. 取消/删除需要用户在页面执行确认动作；邮件扫描器打开 GET 链接不能自动取消或确认订阅。

设计原型位于 `docs/ui-preview/`。其中数据和提醒均为示例，不是已完成的真实查询或投递。

## 4. 已确认架构

采用 **Cloudflare Workers + D1 + Cron，邮件通过 Brevo HTTP API**，用户已确认并要求提供注册入口。无需租常驻服务器，在同一平台管理页面、API、持久数据库与定时任务；是否实际满足免费 CPU、官网出网和发信要求需云环境验收。仅实现选定的一套线上架构。

逻辑分层不依赖具体云厂商：

```text
浏览器：查询界面 / 当前设备收藏 / 提醒验证与管理
                     ↓ 同源 API
HTTP 层：输入验证 / 错误分类 / 请求预算 / 限流
                     ↓
应用层：查日历 / 查区间 / 建立提醒 / 验证 / 管理提醒
                     ↓
领域层：上海日期 / 可用状态 / 距离 / 匹配规则 / 通知状态转换
                     ↓
基础设施：官网只读适配 / 共享快照与缓存 / SQL 存储 / 邮件适配

定时任务 → 共享采集 → 更新成功观测 → 匹配已验证提醒
         → 同一事务保存状态与待发邮件 → 邮件发送与重试
```

浏览器不直接访问官网，邮件 API 密钥仅由服务端读取。不能使用内存数组、浏览器 localStorage 或临时文件作为线上提醒数据库。

### 共享采集与平台预算

- 房源列表、站点日历和相同区间请求按参数共享，不按订阅用户各拉一遍。
- 固定并发上限、短缓存、相同在途请求合并、上游超时和退避；网页刷新不能无限强制刷新上游。
- Worker 免费档当前每次调用最多 50 个外部子请求，D1 还有每调用 50 条查询限制。本次列表有 90 个站点，因此分批采集、持久游标/租约和采集/提醒独立 Cron 都已实现；不能把全市查询直接搬进一次请求。
- 前台读取已有成功快照，显示时间与覆盖率。后台更新中不能把新旧不同时刻的数据包装成同一批完整实时数据。
- 区间监控按相同站点/日期区间去重，并设置总任务量上限；不能允许任意用户创建无限日期组合。
- 本地开发提供假数据和假邮件适配，便于无云账号时完整验证交互、状态与失败恢复。

## 5. 数据和错误语义

| 状态 | 含义 | UI / 提醒处理 |
| --- | --- | --- |
| `not-open` | 按查询规则尚未开放申请 | 明确文字，不显示 0，不触发 |
| `known` 且 count > 0 | 官网成功返回有效正数 | 展示数量，允许匹配 |
| `known` 且 count = 0 | 官网成功返回有效零值 | 展示当前查询到 0 间 |
| `unknown` | 缺失日期、格式异常或请求失败 | 显示未获取，不推断无房，不重置通知状态 |
| `stale` | 曾成功获取，现已过新鲜度窗口 | 显示原时间和过期提示，不作为新通知依据 |

业务日期统一 `Asia/Shanghai`；时钟可以注入测试。当前代码的“今天 + 2 天”规则需要用官方页面再次核对，未完成核对时不能声称它是已验证的长期官方规则。

API 区分输入错误、上游失败、上游超时和服务内部故障；公开响应不包含密钥、邮箱列表或上游原始异常正文。单站失败允许返回部分结果，并带成功站点数/查询站点数和更新时间。

## 6. 提醒可靠性与最小安全设计

- 持久保存邮箱验证状态、提醒条件/版本、成功观测、匹配状态和待发邮件。
- 建立提醒采用验证码或一次性随机令牌；数据库只保存验证/管理令牌摘要；令牌带用途和有效期，管理链接不进入日志或第三方分析。
- 同一提醒持续满足条件时不反复发信；明确不满足后再次满足才重新通知。失败/缺日期不是“不满足”。
- 条件状态变化与待发邮件在一个事务中保存；事件唯一键、发送租约和渠道幂等能力减少重复。
- 发送前再次检查提醒仍启用、条件版本一致、结果仍新鲜。网络失败和服务商 429/5xx 退避重试；永久错误停止重试并记录可诊断状态。
- 重启或重复定时调用后可以恢复，不漏掉已入队的通知。服务商收信但响应丢失仍可能重复，不能承诺不受条件限制的“恰好一次投递”。
- 公开创建接口需要速率限制、每邮箱提醒数上限、验证邮件冷却和每日邮件总预算，防止免费额度被滥用。必要时增加 Cloudflare Turnstile，是否启用以实际验证和滥用风险决定。
- 设置同源策略、CSP、`nosniff`、请求体大小限制、固定官网路径和邮件服务地址。客户端不能自选 owner 或任意服务端抓取网址。
- 邮箱属于业务私有数据；提供取消与删除入口，明确保留范围。不得把真实邮箱或管理链接写进 fixture、截图、提交或公开 UI。
